# 2단계 설계: 팀 공간

작성일: 2026-11-05. 2단계-1 설계(`2026-10-26-phase2-accounts-and-roles-design.md`)의 계정과 역할을 그대로 쓴다. 디자인은 `DESIGN.md`를 따른다.

표시: **(사용자)** 사용자가 정함, **(자료)** 2026-10-01 홈페이지 구조 자료, **(Claude)** Claude가 정함. 사용자가 뒤집을 수 있다.

## 1. 왜 만드나

예전 사이트의 문제는 세 가지였다. 디자인이 별로였고, 동아리 소유가 아니었고, 팀이 무언가 올릴 곳이 없었다. 앞의 둘은 1단계로 해결했다. 남은 것이 팀 공간이다. **(사용자)**

운영진이 소식이나 멘토를 고치는 일은 당분간 지금 방식으로도 할 수 있다. 팀이 글을 못 올리는 쪽이 더 곤란하므로 순서를 바꾼다. **(사용자)**

바뀐 2단계 순서: 로그인과 권한(완료) → **팀 공간(이 문서)** → 운영진 관리 화면 → 회원 커뮤니티.

## 2. 목표, 비목표, 실패 조건

**목표**

- 누구나 창업팀 목록을 보고, 분야와 기수로 거를 수 있다. **(자료)**
- 팀을 누르면 팀 소개 페이지가 나오고, 아래에 그 팀의 게시글이 이어진다. **(사용자)**
- 소개 페이지에 SNS와 홈페이지 링크가 있다. **(자료)**
- 팀원이 로그인해서 자기 팀의 소개를 고치고 글을 올린다. **(자료, 사용자)**
- 글을 올릴 때 **완전 공개**와 **가입자만** 중에서 고른다. **(사용자)**
- 운영진이 팀을 만들고 팀원을 넣으며, 문제 있는 글을 숨길 수 있다.

**비목표**

- 답글, 좋아요, 신고, 알림. 답글은 회원 커뮤니티에서 다룬다.
- 소식, 멘토, 행사 기록 편집. 운영진 관리 화면에서 다룬다.
- 팀 내용의 AI 영어 번역. 입력한 언어 그대로 보여 준다. 메뉴와 버튼 같은 화면 문구만 두 언어로 제공한다.
- 팀 삭제. 공개를 끄는 것으로 대신한다.

**실패 조건 (동작하더라도 실패로 본다)**

- 로그인하지 않은 사람이 가입자 전용 글의 제목, 내용, 사진을 볼 수 있다.
- 다른 팀 사람이 남의 팀 소개나 글을 고칠 수 있다.
- 공개 페이지에 팀이 직접 적지 않은 개인정보(이름, 이메일, 학교 등 가입 정보)가 나온다.
- 글쓰기 화면이 복잡해서 팀원이 설명 없이 글을 못 올린다.
- 사이트의 나머지 부분과 다른 사이트처럼 보인다.

## 3. 화면

주소는 언어 경로를 따른다. 메뉴에 **창업팀**(Startups)을 추가한다.

1. **창업팀 목록** `/startups`: 공개된 팀의 로고, 이름, 한 줄 소개, 분야, 기수. 분야와 기수 필터는 주소에 남는다. 팀이 없으면 빈 화면 문구를 보여 준다.
2. **팀 페이지** `/startups/[slug]`: 위쪽은 로고, 이름, 분야, 기수, 소개, 링크. 아래는 게시글 목록(최신순, 10개씩). 그 팀의 팀원에게는 "소개 수정"과 "글쓰기"가 보인다.
3. **글 페이지** `/startups/[slug]/posts/[id]`: 제목, 날짜, 본문, 사진. 팀원에게는 수정과 삭제가 보인다.
4. **글쓰기·수정**: 제목, 본문, 사진, 공개 범위. 공개 범위는 알약 버튼 둘이고 처음에는 완전 공개가 골라져 있다. 쓴 뒤에도 바꿀 수 있다. **(사용자 확인)**
5. **소개 수정**: 로고, 표지 사진, 한 줄 소개, 소개, 링크. 표지 사진을 고르지 않으면 최신 공개 글의 첫 사진이 나온다. **(사용자)**
6. **팀 관리** `/admin/teams` (운영진 이상): 팀 만들기, 이름·분야·기수 수정(주소는 만들 때 자동으로 생기고 바뀌지 않는다, **사용자**), 공개 켜기·끄기, 팀원 넣기·빼기, 숨긴 글 보기와 되돌리기.

화면의 구체적인 모양은 만들기 전에 `impeccable shape`로 정한다. 관리 화면은 회원 관리 화면의 틀을 따른다.

## 4. 누가 무엇을 하나

| 할 일 | 비로그인 | 가입자·회원(팀 밖) | 그 팀의 팀원 | 운영진·관리자 |
|---|---|---|---|---|
| 공개된 팀 목록과 소개 보기 | O | O | O | O |
| 완전 공개 글 보기 | O | O | O | O |
| 가입자 전용 글 보기 | 안내만 | O | O | O |
| 소개 고치기 | | | O | O |
| 글 쓰기·고치기·지우기 | | | O | 지우기만 |
| 글 숨기기·되돌리기 | | | | O |
| 팀 만들기, 이름·분야·기수·공개 설정, 팀원 관리 | | | | O |

- 팀은 **운영진이 만들고 팀원을 넣는다.** 팀 스스로 등록하면 아무 가입자나 창업팀을 만들 수 있게 되기 때문이다. **(Claude)**
- 팀원은 **회원 이상**만 될 수 있다. 2-1에서 글쓰기를 회원부터로 정했다. 가입자를 넣으려 하면 먼저 회원으로 바꾸라고 안내한다. **(Claude)**
- 한 사람이 여러 팀에 속할 수 있고, 팀원끼리 권한은 같다. 팀장 구분은 두지 않는다. **(Claude)**
- 운영진은 팀 글을 대신 쓰지 않는다. 쓰려면 팀원으로 들어간다. **(Claude)**
- 만든 팀은 처음에 비공개다. 소개가 채워지면 운영진이 공개를 켠다. 공개할 팀의 기준(전체인지 동의한 팀만인지)은 동아리가 정하고, 사이트는 켜진 팀만 보여 준다. **(Claude)**
- "가입자"는 가입 정보 입력을 마친 계정이다. 차단된 계정은 전용 글을 볼 수 없다. **(Claude)**
- 가입자 전용 글은 로그인하지 않은 사람에게 제목도 보이지 않는다. 글이 있으면 "가입자 전용 글이 N개 있어요. 로그인하면 볼 수 있어요"라고 안내한다. **(사용자 확인)** 주소로 바로 들어오면 다른 없는 페이지와 똑같이 404다.

## 5. 내용 규칙

- **작성자는 팀 이름으로만 표시한다.** 개인 이름은 공개 페이지에 나오지 않는다. `PRODUCT.md`가 이름 공개에 동의를 요구하고, 가입 정보를 공개 페이지로 내보내지 않기 위해서다. DB에는 누가 썼는지 기록한다. **(Claude)**
- 팀원 소개가 필요하면 팀이 소개 칸에 직접 적는다. 팀원 명단을 자동으로 보여 주지 않는다. **(Claude)**
- 본문은 **일반 텍스트**다. 줄바꿈을 유지하고, `http`·`https` 주소만 링크로 바꾼다. HTML과 마크다운은 쓰지 않는다. **(Claude)**
- **글마다 사진을 4장까지** 올린다. 한 장에 5MB 이하, JPEG·PNG·WebP. 로고도 같은 형식으로 2MB 이하. 다른 파일은 받지 않는다. **(Claude)**
- 길이 제한: 이름 50자, 한 줄 소개 80자, 소개 2,000자, 글 제목 100자, 본문 5,000자, 링크 5개.
- 링크는 홈페이지, 인스타그램, LinkedIn, 기타 중에서 고른다. `http`·`https`만 받는다.
- 분야는 코드에 둔 고정 목록에서 고르고, 목록 값은 구현 때 실제 팀에 맞춰 사용자에게 확인받는다. 기수는 숫자다. **(Claude)**
- 글을 고치면 수정 시각을 함께 보여 준다.

## 6. 데이터와 권한

DB 작업 전에 `supabase`, `supabase-postgres-best-practices` 스킬과 최신 Supabase 문서를 확인한다.

- 테이블: 팀, 팀원(팀과 계정의 연결), 팀 링크, 글, 글 사진. 이름은 구현 때 정한다.
- **모든 테이블에 RLS를 켜고, 4절의 표를 그대로 정책으로 옮긴다.** 권한 판단은 2-1처럼 토큰이 아니라 `user_roles`와 팀원 테이블을 읽어서 한다. 강등, 차단, 팀에서 빠지는 일이 다음 요청부터 바로 적용된다.
- 2-1은 비로그인(anon)에 아무 권한도 주지 않았다. 이번에 처음으로 **공개된 팀과, 공개된 팀의 숨기지 않은 완전 공개 글**에만 anon 읽기를 연다. 가입 정보 테이블은 그대로 닫아 둔다.
- 쓰기는 비밀키가 아니라 **로그인한 사람의 권한으로** 한다. RLS가 마지막 관문이 되게 하기 위해서다. 팀원이 고칠 수 있는 칸과 운영진만 고칠 수 있는 칸(이름, 주소, 분야, 기수, 공개 설정, 숨김)은 DB에서 나눈다.
- 비공개 팀의 글은 공개 범위와 상관없이 팀원과 운영진만 본다.
- 가입자 전용 글 개수는 숫자만 돌려주는 함수로 비로그인에게 알려 준다. 제목이나 날짜는 돌려주지 않는다.
- **사진은 비공개 저장소에 두고**, 글을 읽을 권한을 확인한 뒤 서명된 주소로 보여 준다. 공개 저장소에 두면 주소만으로 가입자 전용 사진이 열리고, 글의 공개 범위를 바꿔도 사진 주소가 그대로 살아 있기 때문이다. 저장소 정책도 글의 공개 범위를 따른다. 로고는 공개 저장소에 둔다.
- 업로드할 때 크기와 형식을 서버와 저장소 양쪽에서 검사한다.
- 탈퇴: 글은 팀의 내용이므로 남기고, 글에 적힌 작성자 기록만 지운다. 글을 지우면 사진도 지운다. **(Claude)**

## 7. 스위치와 공개

- 2-1의 `NEXT_PUBLIC_AUTH_ENABLED` 스위치를 그대로 쓴다. 꺼져 있으면 `/startups` 전체가 404이고 메뉴에도 없다. 지금 실제 사이트는 달라지지 않는다.
- 로그인을 켤 때 팀 공간도 함께 열린다. 팀 데이터는 그때 운영용 프로젝트에 운영진이 입력한다. 넣어 둘 시드 데이터는 없다.
- 검색 차단(noindex)은 사이트 전체 설정을 따른다.

## 8. 개인정보 처리방침

로그인을 켜기 직전, 초안을 아래 내용으로 고쳐서 **승인을 받는다.**

- 수집·이용 목적에 팀 공간 운영을 넣는다.
- 글의 작성자 기록, 업로드한 사진을 항목에 넣는다.
- 탈퇴해도 팀 글은 남고 작성자 기록만 지워진다는 점을 보유 기간에 적는다.
- 사진 속 인물과 글에 적은 개인정보는 글을 쓰는 팀원이 책임진다는 안내를 글쓰기 화면과 방침에 넣는다.

## 9. 테스트

- pgTAP: 4절 표의 모든 칸(역할별 읽기·쓰기), 비공개 팀, 숨긴 글, 차단 계정, 팀에서 빠진 뒤, 저장소 정책.
- 단위 테스트: 입력 검사, 링크 변환, 필터 주소.
- e2e: 비로그인이 전용 글을 못 보는 것, 팀원이 글을 올리고 공개 범위를 바꾸는 것, 다른 팀이 못 고치는 것, 운영진이 숨기는 것, 스위치를 끄면 404인 것, 두 언어, 모바일, 접근성.

## 10. 진행 방식

- 2-2부터 정한 가벼운 방식으로 한다. 직접 구현하고, 마지막에 브랜치 전체 리뷰를 한 번 한다. RLS와 저장소 정책만 별도로 검토한다.
- 권한이 바뀌므로 merge 전에 `/security-review`를 돌린다.
- 작업 브랜치는 `phase2-accounts`를 이어 쓴다. Vercel의 개발용 Supabase 환경변수가 이 브랜치에만 걸려 있어 미리보기가 바로 동작한다. **(Claude)**
- 운영진 관리 화면과 회원 커뮤니티는 이 문서가 끝난 뒤 따로 설계한다.
