- 작성일: 2026-11-05
- 상태: 확정 (2026-11-05, §10의 1~3번 사용자 결정. 4번 수상 목록은 미정이며 홈 수상 숫자만 그때까지 보류)
- 관련 문서: [`PRODUCT.md`](../../../PRODUCT.md), [`DESIGN.md`](../../../DESIGN.md), 1단계 설계 [`2026-10-03-phase1-foundation-public-pages-design.md`](2026-10-03-phase1-foundation-public-pages-design.md), 2단계-1 설계 [`2026-10-26-phase2-accounts-and-roles-design.md`](2026-10-26-phase2-accounts-and-roles-design.md)

## 1. 왜 만드나

사용자가 정한 사이트 구조(2026-11-05)에서 아직 없는 부분은 아래와 같다.

| 구조 | 빠진 것 |
|---|---|
| 홈 | 최근 소식(아카이브에서 자동 노출), 숫자의 "수상" |
| 02 Startups | 페이지 전체 |
| 03 Network | MOU 기업 상세 페이지 |
| 04 Archive & News | 페이지 전체 (사진, 언론, 수상, 프로젝트·프로그램 기록, 소식, 종류·연도·기수 필터) |
| 05 Contact | SNS 채널 |

구조의 운영 방식은 "팀 상세 페이지는 각 팀이, 그 외 페이지는 운영진이 관리"다. 지금 사이트의 내용은 `src/content/data`의 정적 파일이라 개발자만 고칠 수 있다. 그래서 운영진이 로그인해서 내용을 쓰는 관리 화면이 먼저 있어야 한다.

## 2. 이 문서의 범위

2단계-1 설계는 운영진 관리 화면(2번)과 Archive 필터(1단계 로드맵의 4단계)를 따로 두었다. 이 문서는 둘을 **합친다**. Archive는 운영진이 쓰는 기록을 그대로 보여주는 페이지이고, 홈의 "최근 소식"도 같은 기록에서 나온다. 데이터 구조를 한 번에 정해야 두 화면이 어긋나지 않는다.

| 순서 | 내용 | 문서 |
|---|---|---|
| 2-1 | 로그인과 권한 | 완료 |
| **2-2 (이 문서)** | 운영진 관리 화면, Archive & News 페이지, 홈 최근 소식, 홈 숫자 "수상" | 이 문서 |
| 2-3 | Startups: 팀 목록과 필터, 팀 상세, 팀이 자기 팀만 수정 (2단계-1의 "팀 스페이스"와 합쳐짐) | 다음 문서 |
| 2-4 | MOU 기업 상세 페이지, 파트너 로고 (사용 허락이 오면) | 다음 문서 |
| 이후 | 회원 커뮤니티(게시글, 답글), Contact 문의 폼, Join 모집 기능 | |

Startups를 2-3으로 둔 이유: 팀 상세 페이지는 팀 계정과 "자기 팀만 수정" 권한이 새로 필요해서 범위가 크다. 반면 Archive는 이미 있는 운영진 권한만 쓴다.

## 3. 목표, 비목표, 실패 조건

**목표**

- 운영진이 로그인해서 **기록**(소식, 행사·활동, 언론 보도, 수상, 프로젝트·프로그램)을 쓰고, 고치고, 공개하고, 내릴 수 있다.
- 기록에 사진을 여러 장 올릴 수 있다. 사진은 올리는 순간 사이트에 맞는 크기로 줄어든다.
- 방문자는 `/archive`에서 기록을 종류·연도·기수로 거르고, 기록마다 상세 페이지를 본다.
- 홈에 최근 기록 3개가 자동으로 나온다.
- 홈 숫자에 "수상"이 나온다. 수상 기록의 개수에서 자동으로 계산된다.
- 운영진은 멘토와 파트너도 관리 화면에서 고친다.
- 한국어와 영어 두 언어로 공개된다.

**비목표**

- Startups와 팀 계정 (2-3).
- 홈 첫 화면 문구, 5 Step, 프로그램 설명, FAQ, 혜택, 모집 상태, 여정 도장. 자주 바뀌지 않으므로 이번에는 정적 파일 그대로 둔다(§10 결정 2).
- 글 편집기의 굵게·표·제목 같은 서식. 문단과 링크만 쓴다.
- 예약 공개, 수정 이력 되돌리기, 댓글.

**실패 조건 (동작하더라도 실패로 본다)**

- 개발을 모르는 운영진이 글 하나를 올리는 데 헷갈리거나, 개발자에게 물어봐야 한다.
- 영어 내용이 비어 있거나 기계 번역 그대로인 채 영어 페이지에 공개된다.
- 쓰다 만 글(비공개)이 방문자에게 보인다.
- 사진 원본(수 MB)이 그대로 올라가 페이지가 느려진다.
- 공개 페이지가 지금보다 느려진다(정적 생성이 깨진다).
- 게시 동의를 받지 않은 사람의 이름이나 얼굴 사진이 올라간다. 관리 화면에서 막을 수는 없으므로 확인 문구로 알린다(§5).

## 4. 기록의 종류와 항목

기록은 하나의 표에 담고 **종류**로 나눈다. 사용자 구조의 Archive 항목과 1:1로 맞춘다.

| 종류 | 사용자 구조의 항목 | 예 |
|---|---|---|
| 소식 | 주요 소식 및 행사 안내 | 2기 모집 안내, SHOW CASE 예고 |
| 행사·활동 | 행사 및 활동 사진 | 1차 워크숍, London IR |
| 언론 | 언론 보도 및 기사 | 에듀플러스 2026.01.31 |
| 수상 | 수상 및 주요 성과 | AI+X 경진대회 대상 SL:IT |
| 프로젝트 | 프로젝트 / 프로그램 기록 | VCC 2기 결과 |

| 항목 | 규칙 |
|---|---|
| 종류 | 위 다섯 중 하나. 필수 |
| 제목 | 한국어·영어. 필수 |
| 날짜 | 행사가 있었던 날(또는 기사 날짜). 연도·월만 알아도 된다(`YYYY`, `YYYY-MM`, `YYYY-MM-DD`, 지금 도장 데이터와 같다). 필수 |
| 기수 | 1기, 2기, ... 또는 "기수 없음". 필수 |
| 본문 | 한국어·영어. 문단과 링크만. 언론 기록은 비워도 된다 |
| 요약 | 목록과 홈 카드에 나오는 한두 줄. 한국어·영어. 비우면 본문 앞부분을 쓴다 |
| 사진 | 0장 이상. 사진마다 대체 텍스트(한국어·영어)와 출처. 첫 장이 대표 사진 |
| 외부 링크 | 기사 주소, 영상 주소 등. 언론은 매체 이름과 기사 주소가 필수 |
| 수상 정보 | 수상 기록만: 상 이름, 받은 팀, 대회 이름 |
| 상태 | 쓰는 중 / 공개 |
| 주소 이름 | `/archive/<주소 이름>`. 처음 저장할 때 영어 제목으로 자동으로 만들고, 공개 뒤에는 바뀌지 않는다 |

- 지금 정적 파일의 언론 보도 2건과 활동 사진은 첫 마이그레이션 때 기록으로 옮긴다. 이미 레포에 공개된 내용이라 시드 파일로 옮겨도 된다.
- **영어가 비어 있으면 공개할 수 없다.** 1단계 규칙("두 언어 모두 필수")을 그대로 지킨다. 영어는 운영진이 한국어를 쓸 때 번역해서 함께 넣는다. 사이트가 번역을 대신하지 않는다(§10 결정 3).

## 5. 화면

모든 화면은 1단계의 무대 세계를 따른다(`DESIGN.md`). 관리 화면은 2단계-1의 회원 관리 화면과 같은 틀이다. 화면 단위 UI 설계는 구현 전에 `impeccable shape`로 시안을 만들어 사용자가 고른다.

### 관리 화면 (운영진, 관리자)

계정 메뉴의 "관리" 아래에 **회원 / 기록 / 멘토 / 파트너** 탭을 둔다.

1. **기록 목록**: 종류·상태로 거르기, 제목 검색. 표에는 제목, 종류, 날짜, 기수, 상태, 마지막 수정(누가, 언제). 맨 위에 "새 기록" 버튼.
2. **기록 쓰기**: 종류를 먼저 고르면 그 종류에 필요한 칸만 나온다(언론이면 매체와 기사 주소, 수상이면 상 이름과 팀). 한국어와 영어는 탭이 아니라 **나란히** 둔다. 빠뜨린 칸이 한눈에 보이게 하려는 것이다. 아래에 "임시 저장"과 "공개" 버튼. 공개하기 전에 빠진 칸을 알려준다.
3. **사진 올리기**: 끌어다 놓거나 휴대폰에서 고른다. 올리면 바로 미리보기가 나오고, 대체 텍스트를 쓰게 한다. "사진 속 사람에게 게시 동의를 받았습니다" 확인을 받아야 공개된다(PRODUCT.md의 제약).
4. **멘토, 파트너**: 지금 정적 파일의 항목 그대로 고치는 표. 파트너 로고는 "사용 허락 확인" 칸을 체크해야 보인다(지금 `logoApproved` 규칙).
5. **공개 / 내리기 / 지우기**: 공개된 기록을 내리면 다시 "쓰는 중"이 된다. 지우기는 한 번 더 확인받는다.

### 공개 화면

1. **`/archive`**: 페이지 표지(다른 안쪽 페이지와 같은 `PageCover`), 그 아래 필터 줄(종류, 연도, 기수)과 기록 목록. 필터는 주소에 남겨서(`/archive?kind=award&year=2026`) 링크로 공유할 수 있다. 목록은 날짜 최신순이고 대표 사진이 있는 카드다.
2. **`/archive/<주소 이름>`**: 제목, 날짜, 종류, 기수, 사진, 본문, 외부 링크. 언론 기록은 상세 페이지 없이 기사로 바로 연결할 수도 있다(구현 때 정함).
3. **홈 최근 소식**: 공개된 기록 중 최신 3개를 카드로. 홈의 Global 장 뒤, 마지막 지원 권유 앞에 둔다. "Archive 전체 보기" 링크.
4. **홈 숫자 "수상"**: 지금 숫자 줄(멤버, 창업팀, 멘토)에 수상 개수를 더한다. 기준은 "수상 기록 n건, 날짜 기준"으로 자동 표시.
5. **메뉴**: 홈, About, Network, **Archive**, Contact, Join. Startups는 2-3이 끝날 때 넣는다.

## 6. 권한

2단계-1의 역할을 그대로 쓴다.

| 누가 | 할 수 있는 일 |
|---|---|
| 누구나(로그인 없이) | 공개된 기록, 멘토, 파트너 보기 |
| 운영진, 관리자 | 모든 기록 보기(쓰는 중 포함), 쓰기, 고치기, 공개, 내리기, 지우기. 멘토와 파트너 고치기. 사진 올리기와 지우기 |
| 회원, 가입자 | 공개된 것만 보기 (관리 화면 없음) |

- 운영진이 쓴 내용은 승인 없이 바로 공개된다(2단계-1의 사용자 결정).
- 모든 표에 RLS를 켜고, 권한마다 DB 테스트를 붙인다. 쓰기 권한은 `private.is_at_least('operator')`로 확인한다(2단계-1 §14).
- 사진 저장소(Supabase Storage)도 같은 규칙이다. 읽기는 누구나, 쓰기와 지우기는 운영진부터.

## 7. 어떻게 만드나

**Claude가 정한 기본안 (사용자가 읽으면서 확인)**

- 기록은 Supabase Postgres 표에 둔다. 한국어·영어 칸을 따로 둔다(`title_ko`, `title_en` 같은 방식, 정확한 구조는 구현 때 `supabase-postgres-best-practices`를 따른다).
- `src/lib/content.ts`의 `getPress()`, `getMentors()`, `getPartners()`는 함수 안쪽만 Supabase 읽기로 바꾼다. 1단계 설계가 처음부터 노린 방식이라 페이지 코드는 거의 바뀌지 않는다. 기록 읽기 함수(`getRecords()` 등)를 새로 만든다.
- **공개 페이지는 계속 정적 생성이다.** 운영진이 공개·수정·삭제하면 서버가 해당 페이지의 캐시만 새로 만든다. 정확한 API(Next.js 16의 캐시 무효화)는 구현 전에 `node_modules/next/dist/docs/`에서 확인한다.
- 사진은 서버에서 받아 `sharp`로 줄인다(긴 변 2400px, JPEG, 메타데이터 제거. 지금 레포 사진과 같은 기준). 위치 정보가 든 메타데이터를 지우는 것이 개인정보 면에서도 필요하다. Vercel 함수의 요청 크기 한도 때문에 큰 원본을 받는 방법(브라우저에서 먼저 줄이기 또는 Storage에 직접 올린 뒤 줄이기)은 구현 때 정한다.
- 무료 플랜 Storage 1GB 기준으로, 줄인 사진(장당 약 400KB)은 약 2,500장이 들어간다. 80%가 차면 관리 화면에 알림을 띄운다.
- 지금 정적 파일의 언론, 멘토, 파트너, 활동 사진은 마이그레이션 시드로 옮긴다. 옮긴 뒤 정적 파일과 zod 스키마는 지우고, zod 스키마는 관리 화면의 입력 검사로 다시 쓴다.
- 레포의 `public/images/activities` 사진은 Storage로 옮긴다. 옮기기 전까지는 두 곳을 모두 읽는다.
- 본문은 문단과 링크만 허용하는 일반 텍스트로 저장하고, 화면에 낼 때 HTML로 바꾼다. HTML을 그대로 저장하지 않는다(스크립트 주입을 막기 위해).
- 관리 화면의 저장은 서버 액션으로 하고, 서버에서 DB의 현재 역할을 다시 확인한다(2단계-1과 같다).

## 8. 사용자가 직접 해야 하는 일

1. 수상 기록에 넣을 목록 주기(§10 4번).
2. 운영용 Supabase 프로젝트에 마이그레이션 올리기(2단계-1과 같은 절차, Claude가 명령을 안내).
3. 운영진에게 관리 화면 사용법 공유. `CONTRIBUTING.md`가 아니라 운영진용 짧은 안내를 따로 쓴다.

## 9. 완료 기준

- 운영진이 기록을 쓰고, 사진을 올리고, 공개하고, 내리고, 지울 수 있다(한국어, 영어).
- 영어가 빠진 기록은 공개할 수 없다.
- 쓰는 중인 기록은 운영진 밖의 누구에게도 보이지 않는다(DB 테스트와 화면 테스트).
- `/archive`에서 종류·연도·기수 필터가 되고, 필터가 주소에 남는다.
- 홈에 최근 기록 3개와 수상 개수가 나온다.
- 공개하면 몇 초 안에 공개 페이지에 반영되고, 공개 페이지는 지금처럼 정적으로 뜬다.
- 올린 사진은 2400px 이하이고 메타데이터가 없다.
- 기존 1단계·2단계-1 테스트가 그대로 통과한다.
- 권한이 바뀌는 PR이므로 merge 전에 `/security-review`를 돌린다.

## 10. 사용자 결정 (2026-11-05)

1. **범위**: 운영진 관리 화면과 Archive & News를 한 단계로 합치고, Startups는 다음 단계(2-3)로 둔다.
2. **이번에 관리 화면으로 옮길 내용**: 기록, 멘토, 파트너만. FAQ·혜택·여정 도장은 정적 파일 그대로 두고, 모집 상태는 5단계 모집 기능 때 옮긴다.
3. **영어 내용**: 운영진이 한국어를 쓸 때 영어로 번역해서 함께 넣는다. 새로 써야 하는 영어 글은 없어서 번역 API(Claude API 등)는 쓰지 않는다. 그래서 API 키와 사용료도 없다. 관리 화면은 영어 칸이 비면 공개 버튼 옆에 "영어가 비어 있습니다"를 보여줄 뿐이다.
4. **수상 기록 (미정)**: 홈에 수상 개수를 띄우려면 실제 수상 목록이 필요하다. 지금 자료에 있는 것은 AI+X 경진대회 3건(대상 SL:IT, 최우수상 roAmigo, 우수상 VIETMEDX³)과 카카오모빌리티 워크숍 3건(최우수상 안전상점, 우수상 MORTON, 곁은)이다.
   - AI+X 경진대회는 RISE CREW가 공동 주최한 대회라, 수상팀이 RISE CREW 팀이 아닐 수 있다. 이것을 "RISE CREW의 수상"으로 셀지 정해야 한다.
   - 외부 대회에서 RISE CREW 팀이 받은 상이 더 있으면 목록을 받아야 한다.
   - 정하기 전까지는 홈 숫자에 수상을 넣지 않는다(근거 없는 숫자를 띄우지 않는다). 수상 기록 자체는 다른 기록처럼 쓰고 공개할 수 있다.

## 11. 만드는 사람에게 맡기는 것

- 정확한 테이블 구조, 열 이름, 인덱스, 마이그레이션 나누기.
- 컴포넌트와 파일 구조, 서버 액션의 나눔.
- 관리 화면 표의 페이지 나누기와 정렬.
- 목록 카드와 상세 페이지의 세부 디자인(`impeccable shape` 시안을 사용자가 고른 뒤).
- 로컬 개발용 시드 데이터(가짜 값, 또는 이미 공개된 내용만).

## 12. 위험과 미정 사항

- **공식 인스타그램 계정**이 아직 미정이라 Contact의 SNS 채널을 넣지 못한다. 정해지면 이 단계와 상관없이 바로 넣는다.
- **파트너 로고**는 사용 허락이 와야 넣는다(2-4).
- **사진 속 사람의 게시 동의**는 관리 화면이 확인 문구만 받을 뿐, 실제 동의를 검증하지 못한다. 운영진 안내에 적는다.
- **Storage 무료 한도**: §7의 계산은 줄인 사진 기준이다. 한도가 차면 Pro 플랜이나 사진 정리가 필요하다.
- **운영용 프로젝트 일시정지**(2단계-1 §14): 기록을 DB에서 읽게 되면, DB가 멈췄을 때 캐시를 새로 만들 수 없다. 이미 만든 정적 페이지는 그대로 보이지만 새 글은 반영되지 않는다. 일시정지 여부를 출시 전에 확인한다.
