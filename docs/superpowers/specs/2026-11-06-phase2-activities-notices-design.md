# 2단계 설계: 활동 내역과 공지사항

작성일: 2026-11-06. 2단계-1 설계의 계정과 역할, 팀 공간 설계의 관리 화면 틀을 그대로 쓴다. 디자인은 `DESIGN.md`를 따른다. 항목 끝의 **(사용자)**는 사용자가 정한 것, **(Claude)**는 Claude가 정하고 사용자가 확인할 것이다.

## 1. 왜 만드는가

운영진이 사이트 오픈 후 자주 할 일은 팀 페이지를 만들어 가입자를 연결하고, 행사 뒤 활동 내역을 올리고, 공지를 올리는 것이다. **(사용자)** 앞의 것은 `/admin/teams`에 이미 있다. 활동 내역은 코드 파일이라 개발자만 고칠 수 있고, 공지사항은 올릴 곳이 없다.

처음 2단계 계획의 "운영진 관리 화면"(소식, 멘토, 행사 기록, 사이트 내용 수정, AI 번역)을 이 두 가지로 줄인다. 내용을 고칠 일이 많지 않다는 사용자의 판단을 따른다. **(사용자)**

## 2. 범위

**만든다**

- 운영진이 활동 내역을 올리고 고치고 지우는 관리 화면과 공개 활동 페이지
- 운영진이 공지를 올리고 고치고 지우는 관리 화면과 공개 공지 페이지
- 코드에 있는 활동 15건을 DB로 옮기기

**만들지 않는다**

- AI 번역 버튼. 비용이 들고 글이 적어, 필요하면 무료 번역 화면에서 붙여 넣는다. 나중에 버튼만 더할 수 있게 영어 칸을 둔다. **(사용자)**
- 멘토, 파트너, FAQ, 숫자, 프로그램, 모집 상태 편집. 당분간 개발자가 코드 파일로 고친다. **(Claude)**
- 홈 화면 변경. 홈은 고른 행사와 사진으로 짠 구성이라 코드 파일을 계속 읽는다. 새 활동은 홈에 저절로 나오지 않는다. **(Claude)**
- 공지 메일 발송, 알림, 댓글, 초안과 예약 공개. **(Claude)**

## 3. 활동 내역

**입력 칸**

| 칸 | 규칙 |
|---|---|
| 제목 | 한국어 필수, 영어 선택 **(사용자)** |
| 날짜 | 연도, 연-월, 연-월-일 중 하나. 비울 수 있다. 지금 데이터에 세 형식과 날짜 없는 항목이 모두 있다 **(Claude)** |
| 도시 | 한국어 필수, 영어 선택. 해외 활동과 구분하는 데 쓴다 **(사용자)** |
| 사진 | 선택, 한 장. 사진이 없는 기존 활동이 있다 **(Claude)**. 없으면 RISE CREW 로고로 통일한다 **(사용자)** |
| 짧은 설명 | 선택, 500자까지. 한국어, 영어 각각 **(Claude: 글자 수와 선택 여부)** |
| 아직 안 열린 행사 | 체크 칸, 기본값은 꺼짐 **(Claude)** |

영어 칸이 비면 영어 화면에도 한국어를 보여 준다. **(사용자)**

"아직 안 열린 행사"를 켜 두면 날짜 전에는 "예정", 날짜가 지나면 지금 연혁처럼 "확인 필요"로 보인다. 날짜만으로 판단하면 열리지 않은 행사가 날짜가 지났다는 이유로 끝난 활동처럼 보이기 때문이다. **(Claude)**

**보이는 곳**

- `/activities`: 최신순 카드 목록. 제목, 날짜, 도시, 사진, 설명이 카드에 다 있으므로 상세 페이지는 없다. **(Claude)**
- `/about` 연혁: 활동 내역을 함께 보여 준다.

**기존 15건**

마이그레이션으로 옮긴다. 공개 정보이고 코드에도 이미 있는 내용이다. 저장소의 기존 사진 경로(`/images/activities/...`)를 그대로 쓸 수 있어야 한다. 기존 항목의 근거 자료(`evidence`)에는 공개 화면에 보일 URL이 하나도 없으므로 옮기지 않고, 출처 링크 칸도 만들지 않는다. 근거 기록은 `stamps.ts`에 남는다. **(Claude)**

## 4. 공지사항

**입력 칸:** 제목(한국어 필수, 영어 선택), 본문(한국어 필수, 영어 선택, 5000자까지), 맨 위 고정 체크, 사진과 파일 첨부. 본문은 팀 글과 같은 줄글이다. **(Claude)**

**첨부:** 사진과 파일을 첨부할 수 있다. **(사용자)** 사진 4장, 파일 5개, 파일당 10MB까지, PDF·한글·워드·엑셀·파워포인트만 받는다. 파일은 공개 버킷 `notice-files`에 있어 누구나 내려받을 수 있으므로, 작성 화면에 개인정보가 든 파일을 올리지 말라고 적는다. 압축 파일과 브라우저가 실행하는 형식(HTML, SVG)은 받지 않는다. 내려받을 때 원래 파일 이름을 쓴다. **(Claude: 개수, 크기, 형식)**

**보이는 곳:** `/notices`는 고정 글 다음 최신순 목록, `/notices/[id]`는 글 상세. 내용은 모집 안내와 행사 공지이고 **누구나 볼 수 있다.** **(사용자)** 작성일을 보여 주고, 고친 글에는 고친 날짜도 보여 준다. **(Claude)**

## 5. 권한

| 할 일 | 방문자 | 가입자·회원 | 운영진·관리자 |
|---|---|---|---|
| 활동·공지 읽기 | O | O | O |
| 쓰기, 고치기, 지우기 | X | X | O |

- 운영진이 쓴 내용은 승인 없이 바로 공개된다. **(사용자, 2-1 설계)**
- 지우기는 되돌릴 수 없으므로 확인을 한 번 받는다. **(Claude)**
- 쓰기는 로그인한 사람의 권한으로 하고, RLS가 `private.is_at_least('operator')`로 마지막에 확인한다. 팀 공간과 같은 방식이다.
- 사진은 공개 버킷에 저장한다. 올리기와 지우기는 운영진 이상만, 5MB 이하 JPG, PNG, WebP만 받는다. 줄이기는 `src/lib/teams/shrink.ts`, 올리기는 `upload.ts`를 재사용한다.

## 6. 관리 화면

- `/admin/activities`, `/admin/notices`: 목록, 만들기, 고치기, 지우기. `/admin/teams`의 틀을 따른다.
- 계정 메뉴의 관리 항목에서 들어갈 수 있어야 한다. 버튼이 없어 주소를 직접 쳐야 했던 일이 팀 관리에서 있었다.
- 화면의 구체적인 모양은 만들기 전에 `impeccable shape`로 정한다.

## 7. 공개 시점

Production은 로그인 스위치가 꺼져 있고, 운영 DB에는 이번 테이블이 아직 없다. 운영진이 글을 올리려면 로그인이 필요하므로 **로그인과 함께 공개한다.** **(Claude)**

- 스위치가 꺼져 있으면 `/activities`, `/notices`, 관리 화면은 404이고 메뉴에도 없다. 활동과 공지 메뉴도 `/startups`처럼 스위치를 따른다.
- 스위치가 꺼져 있으면 `/about` 연혁은 지금처럼 코드 파일을 읽어 DB를 찾지 않는다. 그래서 `stamps.ts`는 남는다. 홈도 계속 이 파일을 쓴다.
- 스위치를 켠 뒤 `/about` 연혁은 DB를 읽는다. 이후 행사는 DB에만 쌓이고, 홈에 넣고 싶으면 개발자가 `stamps.ts`도 고친다.

공개 전 체크리스트에 운영 DB 마이그레이션과 공개 버킷 확인을 더한다.

## 8. 하지 않을 일과 실패 기준

- 개발을 모르는 운영진이 도움 없이 활동 하나를 올리지 못하면 실패다.
- 운영진이 아닌 계정이 글이나 사진을 바꿀 수 있으면 실패다.
- 스위치가 꺼진 운영 사이트의 모습이 달라지면 실패다.
- 영어 칸이 비었다고 영어 화면이 깨지거나 빈 칸으로 보이면 실패다.

## 9. 확인 방법

- pgTAP: 읽기는 모두 허용, 쓰기와 사진 올리기는 운영진 이상만.
- e2e: 운영진이 활동과 공지를 올리면 공개 화면에 나온다. 고치기, 지우기, 영어가 빈 글의 영어 화면, 고정 순서, 비운영진 거부. 스위치를 끄면 새 주소가 404이고 메뉴에 없으며 `/about`이 그대로다.
- RLS와 저장소 정책이 바뀌므로 merge 전에 `/security-review`를 돌린다.

## 10. 만드는 사람에게 맡기는 것

테이블과 칸 이름, 기존 사진과 새 사진 경로를 함께 담는 방식, 언어 칸 구조, 목록 페이지 나누기, 메시지 문구, 사진 대체 텍스트 처리(제목을 기본으로 쓰되 기존 사진의 설명은 유지).
