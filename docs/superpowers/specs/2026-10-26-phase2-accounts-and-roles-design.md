# 2단계-1 설계: 로그인과 권한

작성일: 2026-10-26. 1단계 설계(`2026-10-03-phase1-foundation-public-pages-design.md`)를 잇는다. 기술 스택, 보안 규칙, 디자인 시스템(`DESIGN.md`)은 그대로 따른다.

## 1. 왜 만드나

1단계 사이트는 정적이라 내용을 바꾸려면 개발자가 코드를 고쳐야 한다. 개발과 유지보수는 개발 팀장(사용자) 한 명이 Claude와 함께 하고, 팀원들은 GitHub 레포의 문서와 PR을 보며 따라온다. 그래서 사이트가 개발자 없이도 살아 있으려면 운영진이 직접 로그인해서 내용을 고칠 수 있어야 한다.

사용자는 여기서 더 나아가 동아리 회원 전체가 로그인해서 게시글을 쓰고, 답글을 달고, 팀 스페이스를 꾸리는 커뮤니티를 원한다. 가입한 비회원(지원을 고민하는 학생 등)의 정보는 지원자 모집에 쓰인다.

이 문서는 그 전체의 바닥인 **계정, 로그인, 역할**만 다룬다.

## 2. 2단계 전체에서의 위치

사용자와 정한 순서. 각 항목은 따로 설계하고 따로 만든다.

1. **로그인과 권한 (이 문서)**: 가입, 로그인, 역할, 회원 관리, 개인정보.
2. **운영진 관리 화면**: 소식 글, 멘토 정보, 행사 기록(결과 소식, 수상팀, 현장 사진), 사이트 곳곳의 내용 수정, AI 영어 번역. 지금 정적 파일(`src/content/data`)의 내용을 DB로 옮긴다.
3. **회원 커뮤니티**: 게시글과 답글.
4. **팀 스페이스**: 팀마다 공간을 꾸린다. 1단계 설계의 3단계(Startups 팀 페이지)와 합쳐진다.

이 문서에서 정한 역할과 권한은 2~4번이 그대로 쓴다.

## 3. 목표, 비목표, 실패 조건

**목표**

- 누구나 구글 계정 또는 이메일 링크로 가입하고 로그인할 수 있다.
- 계정마다 역할(가입자, 회원, 운영진, 관리자)이 있고, 역할에 따라 할 수 있는 일이 다르다.
- 운영진과 관리자가 회원 관리 화면에서 역할을 바꾸고 계정을 차단할 수 있다.
- 가입자는 마이페이지에서 자기 정보를 보고, 고치고, 탈퇴할 수 있다. 탈퇴하면 정보가 지워진다.
- 개인정보 처리방침 페이지가 있고, 가입할 때 동의를 받는다.
- 한국어와 영어 두 언어로 제공한다.

**비목표 (이 문서에서 만들지 않는다)**

- 소식, 멘토, 행사 기록 같은 내용 편집. 2번에서 한다.
- 게시글, 답글, 팀 스페이스. 3·4번에서 한다. 이 문서에서는 역할과 권한만 정한다.
- 지원서 제출 기능(모집). 1단계 로드맵의 5단계 그대로다. 이 문서는 모집에 쓸 정보와 동의만 받아 둔다.
- 카카오 로그인, 전화번호 로그인, 비밀번호 로그인.

**실패 조건 (동작하더라도 실패로 본다)**

- 개발을 모르는 운영진이 회원 관리 화면을 쓰다가 헷갈리거나 실수로 권한을 잘못 준다.
- 꼭 필요한 것보다 많은 개인정보를 모은다(예: 전화번호, 학번).
- 회원이 아닌 가입자가 글을 쓸 수 있거나, 다른 사람의 개인정보(회원 명단 등)를 볼 수 있다.
- 비밀키나 개인정보가 public 레포에 들어간다.
- 로그인 화면과 계정 화면이 1단계 사이트와 다른 사이트처럼 보인다.

## 4. 역할과 권한 (사용자 결정)

| 역할 | 누가 | 할 수 있는 일 |
|---|---|---|
| **가입자** | 가입만 한 사람(지원을 고민하는 학생 등) | 로그인 전용 내용 열람·조회, 마이페이지. **글쓰기·답글 불가.** 가입 정보는 모집에 쓰인다(동의한 경우) |
| **회원** | 동아리에 합격한 사람 | 가입자의 모든 것 + 게시글, 답글, 팀 스페이스(3·4번에서 구현) |
| **운영진** | 운영진 열 몇 명(지도교수 포함, 기수마다 바뀜) | 회원의 모든 것 + 내용 편집과 바로 공개(2번), 문제 있는 글·계정 숨김과 차단, 회원 관리 화면에서 **가입자↔회원** 변경 |
| **관리자** | 개발 팀장(사용자), 이후 새로 들어오는 개발자 | 운영진의 모든 것 + **운영진·관리자 지정과 해제** |

- 가입하면 누구나 **가입자**로 시작한다. 합격자 발표 뒤 운영진이 회원 관리 화면에서 여러 명을 골라 한 번에 회원으로 바꾼다.
- 운영진이 쓴 내용은 승인 없이 바로 공개된다(사용자 결정).
- 기수가 바뀔 때 운영진을 들이고 빼는 일은 관리자가 한다. 새 개발자가 들어오면 관리자가 역할을 넘겨준다. 그 절차는 `CONTRIBUTING.md`에 적는다.
- 차단된 계정은 로그인할 수 없다.
- 공개 사이트(홈, 소개, 네트워크, 문의, 지원 안내)는 지금처럼 로그인 없이 누구나 본다. 로그인 전용 내용(3번의 커뮤니티 등)은 로그인한 사람만 본다.

## 5. 가입과 로그인 흐름 (사용자 결정)

- **누구나 가입**할 수 있다. 회원 명단 사전 등록, 가입 후 승인, 초대 코드, 학교 메일 제한도 검토했지만, 사용자는 "사람이 많이 들어오지 않을 것"이라 보고 누구나 가입을 골랐다. 대신 글쓰기는 회원부터 가능하다.
- 로그인 수단은 **구글**과 **이메일 링크**(메일로 온 링크를 누르면 로그인) 두 가지다.
- 가입과 로그인은 **한 화면**이다. 처음 로그인한 사람은 바로 가입 정보 입력 화면으로 간다. 가입 정보 입력을 마쳐야 가입이 끝난다. 마치지 않고 나가면, 다음 로그인 때 다시 그 화면이 나온다.
- 위쪽 메뉴의 "로그인"은 로그인 뒤 이름 첫 글자 동그라미로 바뀌고, 누르면 마이페이지와 로그아웃이 나온다. 운영진과 관리자에게는 "관리"도 보인다.
- 로그인 화면과 계정 화면의 주소는 언어 경로를 따른다(`/ko/...`, `/en/...`). 로그인 뒤에는 로그인을 누르기 전에 보던 페이지로 돌아간다.

## 6. 가입 정보 (사용자 결정)

| 항목 | 규칙 |
|---|---|
| 이메일 | 로그인한 계정에서 자동으로 가져온다. 입력하지 않는다 |
| 성, 이름 | 두 칸으로 나눠 받는다. 둘 다 필수 |
| 지금 하고 있는 일 | 대학생 / 대학원생 / 졸업생·직장인 / 창업자 / 기타 중 하나. 필수 |
| 학교, 전공 | 대학생·대학원생을 고르면 나타나고 필수 |
| 소속 | 그 밖을 고르면 나타나고 선택(회사나 팀 이름) |
| [필수] 만 14세 이상 확인 | 만 14세 미만은 법정대리인 동의가 필요해서(개인정보 보호법), 가입을 만 14세 이상으로 한정한다. Claude가 정함 |
| [필수] 개인정보 수집·이용 동의 | 동의해야 가입이 끝난다 |
| [선택] 모집 소식 이메일 수신 동의 | 동의한 사람의 정보만 모집 안내에 쓴다 |

- **전화번호는 받지 않는다**(사용자 결정). 학번도 받지 않는다.
- 동의는 언제, 어떤 버전의 처리방침에 동의했는지 함께 기록한다.
- 사용자가 입력한 내용(이름, 학교 등)은 입력한 그대로 저장하고 번역하지 않는다.

## 7. 화면 (사용자가 시안을 보고 결정)

모든 계정 화면은 1단계의 무대 세계를 따른다(`DESIGN.md`). 배경은 어두운 무대색 위에 **위에서 비추는 코발트 조명**(사용자 선택, 안 A)이고, 주 버튼은 라임 알약이다.

1. **로그인** (안 A "무대 한가운데"): 큰 "로그인" 제목, "처음이면 로그인하면서 가입돼요" 안내, 구글로 계속하기 버튼, "또는", 이메일 입력칸과 "로그인 링크 받기" 버튼. 링크를 보낸 뒤에는 "메일함을 확인해 주세요" 상태를 보여준다.
2. **가입 정보 입력**: "반가워요!" 제목, 6절의 항목. 직업 선택은 알약 버튼이고, 고른 직업에 따라 학교·전공 칸 또는 소속 칸이 바뀐다. 아래에 동의 두 줄과 "가입 완료" 버튼.
3. **마이페이지** (가입한 모든 사람): 이름 첫 글자 동그라미, 이름, 이메일, 지금 역할 배지. 아래로 가입 정보 목록, "정보 수정"과 "로그아웃" 버튼, 맨 아래 "회원 탈퇴" 링크. 탈퇴는 한 번 더 확인받는다.
4. **회원 관리** (운영진과 관리자): 이름·이메일 검색, 역할로 거르기, "모집 소식 동의한 사람만" 거르기. 표에는 이름, 이메일, 하고 있는 일, 학교·전공 또는 소속, 모집 소식 동의 여부, 역할이 나온다(사용자 결정). 여러 명을 골라 "회원으로" 바꾸거나 차단한다. 운영진에게는 운영진·관리자 지정 기능이 보이지 않는다. 명단 내려받기(CSV 등)는 만들지 않는다(Claude가 정함: 개인정보가 사이트 밖으로 나가는 통로를 만들지 않으려고. 모집 때 필요해지면 그때 따로 정한다).
5. **개인정보 처리방침**: 사이트 아래쪽(푸터)과 가입 정보 입력 화면에서 연결한다.

브레인스토밍 시안은 `.superpowers/brainstorm/`(레포에 올라가지 않음)에 있다. 시안은 구조와 분위기를 정한 것이고, 실제 크기와 간격은 `DESIGN.md` 규칙대로 만든다.

## 8. 개인정보 (사용자 결정 + 법적 요구)

계정을 받는 순간 개인정보를 처리하게 된다. 개인정보 처리의 주체는 동아리(RISE CREW)다.

- **처리방침 페이지** `/ko/privacy`, `/en/privacy`에 적을 것: 수집 항목(6절), 수집·이용 목적(계정 관리, 커뮤니티 이용, 동의한 경우 모집 안내), 보유 기간(탈퇴할 때까지, 탈퇴하면 바로 삭제), 처리를 맡기는 곳(Supabase, Vercel, Google 로그인), 이용자의 권리(열람·정정·삭제는 마이페이지에서), 보호책임자.
- **개인정보 보호책임자**: "RISE CREW 회장 / risecrew4@gmail.com". 회장은 기수마다 바뀌므로 이름 대신 직책으로 적는다. 실무 담당은 "웹사이트 관리자"로 함께 적는다(사용자 결정).
- 처리방침 초안은 표준 양식에 맞춰 쓰고, **로그인을 켜기 전에 운영진과 ANCHOR 사업단 담당자에게 확인받는다.** 법률 검토가 아니라는 점을 레포 문서에 남긴다.
- **확인이 늦어지면 로그인을 꺼둔 채로 merge한다**(사용자 결정). 로그인 기능 전체(메뉴의 로그인 표시, 로그인·가입·계정 화면)를 환경변수 하나로 켜고 끈다. 꺼져 있으면 메뉴에 로그인이 보이지 않고 계정 화면 주소는 404다. 확인이 오면 운영용 프로젝트에서 켠다. 임시 주소(vercel.app)도 누구나 들어올 수 있으므로, 켜는 순간이 실제 가입이 시작되는 순간이다.
- 탈퇴하면 계정과 가입 정보를 바로 삭제한다.
- 회원 관리 화면에서 운영진과 관리자는 가입 정보 전부(이름, 이메일, 하고 있는 일, 학교·전공·소속, 모집 소식 동의 여부)를 본다(사용자 결정). 처리방침에 "운영진이 회원 관리와, 동의한 경우 모집 안내를 위해 열람한다"고 적는다.
- 가입자는 다른 사람의 정보를 볼 수 없다.

## 9. 어떻게 만드나

사용자가 기본안을 그대로 승인한 것과 Claude가 정한 것을 구분한다.

**사용자가 승인한 기본안**

- 로그인 처리는 Supabase Auth와 공식 Next.js 연동(`@supabase/ssr`, `@supabase/supabase-js`)으로 한다. 세션 갱신은 지금 언어 처리를 하는 `src/proxy.ts` 한곳에서 next-intl과 함께 한다.
- 이메일 링크는 진짜 도메인이 생기기 전까지 RISE CREW Gmail 계정의 SMTP(앱 비밀번호)로 보낸다.
- 개발과 테스트는 내 컴퓨터의 로컬 Supabase(Supabase CLI + Docker)에서 한다.
- DB 변경은 전부 마이그레이션 파일로 레포에 남긴다. 모든 테이블에 RLS를 켜고, 권한별 접근 규칙에는 테스트를 붙인다.
- 클라우드는 지금 개발용 프로젝트 `rise-crew-dev`(서울 리전)만 있다.
- 키는 `.env.local`과 Vercel 환경변수에만 둔다. 레포에는 변수 이름만 적은 `.env.example`을 둔다.
- Claude는 Supabase MCP로 **개발용 프로젝트에만, 읽기 전용으로** 연결한다(오류 로그, 보안 점검용). 인증은 사용자가 터미널에서 한다.

**Claude가 정한 것 (사용자가 읽으면서 확인)**

- 운영용 Supabase 프로젝트는 **이 문서의 작업을 main에 합치기 직전에** 만든다. 실제 사이트에서 로그인을 켜는 순간부터 진짜 계정이 쌓이기 때문이다. 무료 플랜의 2개 한도를 개발용과 운영용으로 쓴다. (처음 계획은 "2번을 열 때"였다.)
- **DB 변경을 클라우드에 올리는 방법**: 관리자가 자기 컴퓨터에서 Supabase CLI로 올린다(`supabase db push` 등, 정확한 명령은 CLI `--help`로 확인). GitHub Actions로 자동 배포하지 않는다. 그러려면 DB 비밀번호와 Supabase 토큰을 GitHub Secrets에 넣어야 하는데, 공개 레포에 쓰기 권한을 가진 협업자가 워크플로를 추가해 빼낼 수 있기 때문이다.
  - 개발용 DB에는 개발 중에 올린다. 운영용 DB에는 PR을 merge하기 직전에 올린다. 그래서 마이그레이션은 직전 버전 코드와도 함께 동작하게(추가 위주로) 쓴다.
  - 구글 로그인, SMTP, 허용 주소, Custom Access Token Hook 같은 Auth 설정도 프로젝트마다 대시보드에서 맞춘다. 로컬은 `supabase/config.toml`에 두고, 클라우드 설정 순서는 README 체크리스트로 남긴다.
- **미리보기 주소의 연결**: Vercel의 Preview 환경변수는 개발용 프로젝트, Production 환경변수는 운영용 프로젝트를 가리킨다. 그래서 PR 미리보기에서 로그인해 보면 개발용 DB에 계정이 생긴다. 개발용 DB의 계정도 실제 사람의 정보이므로 운영용과 똑같이 다룬다.
- 역할은 DB 테이블에 저장하고, Supabase가 권장하는 방식(Custom Access Token Hook)으로 로그인 토큰에 역할 정보를 넣어 RLS에서 쓴다. 사용자가 고칠 수 있는 `user_metadata`는 권한 판단에 절대 쓰지 않는다.
- 역할이 바뀌면 다음 토큰 갱신 때 반영된다. 관리 화면 같은 민감한 서버 화면은 토큰만 믿지 않고 DB의 현재 역할을 다시 확인한다. 차단은 로그인 세션까지 끊어서 바로 막는다.
- 계정 삭제와 차단처럼 관리자 키(secret key)가 필요한 일은 서버에서만 한다. 그 키에는 `NEXT_PUBLIC_` 접두사를 붙이지 않는다.
- 커스텀 SMTP를 쓰면 무료 플랜에서도 인증 메일 문구를 바꿀 수 있다. 로그인 링크 메일을 한국어·영어로 다듬는다.
- 지금 사이트는 대부분 정적 생성(ISR)이다. 로그인 상태가 필요한 부분(메뉴의 로그인 표시, 계정 화면)만 동적으로 만들고, 공개 페이지의 정적 생성과 캐시는 깨지 않는다.

## 10. 사용자가 직접 해야 하는 일

Claude가 대신할 수 없는 일(계정, 비밀번호, 결제, 보안 설정). 각 단계가 필요한 시점에 안내한다.

1. Docker Desktop 설치(개인·교육용 무료).
2. RISE CREW 구글 계정에 2단계 인증을 켜고 Gmail 앱 비밀번호 만들기.
3. Google Cloud Console(RISE CREW 계정)에서 OAuth 클라이언트 만들기. 기본 정보(이메일, 이름)만 써서 구글 심사는 필요 없다.
4. Supabase 대시보드에서 구글 로그인, SMTP, 허용 주소 설정. 키를 `.env.local`과 Vercel 환경변수에 넣기.
5. Supabase MCP 인증(터미널).
6. 운영용 Supabase 프로젝트 만들기(main에 합치기 직전), 운영용 DB에 마이그레이션 올리기(Claude가 명령과 순서를 안내).
7. 처리방침 초안을 운영진과 ANCHOR 사업단 담당자에게 확인받기.

## 11. 완료 기준

- 구글과 이메일 링크로 가입·로그인·로그아웃이 된다(한국어, 영어).
- 처음 로그인하면 가입 정보 입력으로 가고, 입력을 마쳐야 가입이 끝난다.
- 역할별 권한이 RLS와 서버 양쪽에서 지켜진다. 권한별 접근 규칙마다 테스트가 있다(DB 테스트와 화면 테스트).
- 운영진은 가입자↔회원만, 관리자는 모든 역할을 바꿀 수 있다. 차단된 계정은 로그인할 수 없다.
- 마이페이지에서 수정과 탈퇴가 되고, 탈퇴하면 정보가 지워진다.
- 개인정보 처리방침 페이지가 있고, 동의 기록(만 14세 이상 확인 포함)이 남는다.
- 로그인 기능을 환경변수 하나로 켜고 끌 수 있고, 꺼진 상태와 켜진 상태 모두 테스트가 있다.
- 1단계의 모든 테스트가 그대로 통과하고, 공개 페이지는 지금처럼 정적으로 빠르게 뜬다.
- 로그인 전용 화면은 검색엔진 수집 대상에서 뺀다.
- `README.md`, `CONTRIBUTING.md`에 로컬 Supabase 실행법, 환경변수, 역할 넘기기 절차가 있다.
- 로그인·권한 변경이 담긴 PR은 merge 전에 `/security-review`를 돌린다.

## 12. 만드는 사람에게 맡기는 것

- 정확한 테이블 구조, 열 이름, 마이그레이션 나누기. `supabase-postgres-best-practices`를 따른다.
- 컴포넌트와 파일 구조, 서버 액션과 라우트 핸들러의 나눔.
- 화면 문구의 세부 표현(이 문서의 뜻을 벗어나지 않는 선에서).
- 회원 관리 표의 페이지 나누기와 정렬.
- 로컬 개발용 시드 데이터(가짜 값만 쓴다).

## 13. 위험과 미정 사항

- **구글 로그인 화면의 주소**: 구글 동의 화면에 우리 도메인 대신 `...supabase.co`가 보인다. 바꾸려면 Supabase 사용자 지정 도메인(유료)이 필요하다. 지금은 그대로 둔다.
- **Gmail 발송 한도**: Gmail SMTP는 하루 발송량에 한도가 있다. 규모상 충분하지만, 진짜 도메인이 생기면 메일 발송 서비스로 옮긴다.
- **진짜 도메인**: 도메인을 연결하면 Supabase 허용 주소, 구글 OAuth 허용 주소, 메일 링크 주소를 함께 바꿔야 한다. README의 "배포 주소" 절에 체크리스트로 남긴다.
- **무료 플랜 일시정지**: 오래 쓰지 않은 무료 프로젝트는 멈출 수 있다. 개발용은 다시 켜면 되고, 운영용은 사이트 접속이 있어 멈출 일이 적다.
